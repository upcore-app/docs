| Method | Path | Scope |
| --- | --- | --- |
| `GET` | `/api/v1/maintenances` | `maintenances:read` |
| `POST` | `/api/v1/maintenances` | `maintenances:write` |
| `GET` | `/api/v1/maintenances/{id}` | `maintenances:read` |
| `PATCH` | `/api/v1/maintenances/{id}` | `maintenances:write` |
| `DELETE` | `/api/v1/maintenances/{id}` | `maintenances:write` |
| `POST` | `/api/v1/maintenances/{id}/updates` | `maintenances:write` |

Filters on the list route: `status`, `statusPageId`.

Statuses are `scheduled`, `in_progress` and `completed`, and — like incidents —
are moved by posting a timeline update.

## Schedule a window

```bash [Terminal]
curl -X POST https://status.example.com/api/v1/maintenances \
  -H "Authorization: Bearer $UPCORE_KEY" -H 'Content-Type: application/json' \
  -d '{
        "title": "Database upgrade",
        "message": "Planned upgrade, expect brief interruptions.",
        "startsAt": "2026-09-01 22:00:00",
        "endsAt": "2026-09-02T00:30:00Z",
        "statusPageIds": [1],
        "monitors": [
          { "monitorId": 3, "impact": "degraded" },
          { "monitorId": 4, "impact": "down" }
        ]
      }'
```

`endsAt` must be after `startsAt`. A `PATCH` that would invert the window is
rejected.

## Read `active`

The response carries `active`: whether the window is running **right now** —
either explicitly `in_progress`, or still `scheduled` with a start time already
passed.

While a window is active, its monitors are shown as under maintenance on the
status pages it is announced on, each with the `impact` declared for it —
`degraded` or `down`, defaulting to `degraded`.
