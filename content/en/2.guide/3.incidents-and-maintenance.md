A red bar says something is wrong. An incident says *what*, and keeps saying it
as the picture changes.

## Open an incident

An incident carries a title, the status pages it is announced on, and the
monitors it affects — each with an impact of `degraded` or `down`.

It always has at least one timeline entry, so the first message is required. It
is not a field you fill in later.

```json
{
  "title": "Elevated error rates on the API",
  "message": "We are investigating increased 5xx responses.",
  "statusPageIds": [1],
  "monitors": [{ "monitorId": 3, "impact": "degraded" }]
}
```

## Move it along

The lifecycle is four states:

::steps{level="3"}

### investigating

Something is wrong and you are looking at it.

### identified

You know what it is.

### monitoring

The fix is in and you are watching whether it held.

### resolved

Done. `resolvedAt` is stamped.

::

::warning
The status is moved by **posting a timeline update**, never by editing the
incident. A `PATCH` changes the title, the status pages and the affected
monitors — not the state.
::

Every update is a message plus the status it moves to, and the thread is what the
public page shows. Posting a status other than `resolved` after a resolution
clears `resolvedAt` again — that is how an incident is reopened.

![An incident and its timeline — the status is moved by posting an update, never by editing the incident](/screenshots/en/incident-detail.jpg)

## Schedule maintenance

A maintenance window is the same shape with a different lifecycle —
`scheduled`, `in_progress`, `completed` — and a start and end time. `endsAt` must
be after `startsAt`, and an edit that would invert the window is rejected.

```json
{
  "title": "Database upgrade",
  "message": "Planned upgrade, expect brief interruptions.",
  "startsAt": "2026-09-01 22:00:00",
  "endsAt": "2026-09-02T00:30:00Z",
  "statusPageIds": [1],
  "monitors": [
    { "monitorId": 3, "impact": "degraded" },
    { "monitorId": 4, "impact": "down" }
  ]
}
```

While a window is **active** — explicitly `in_progress`, or still `scheduled`
with a start time already passed — its monitors are shown as under maintenance on
the pages it is announced on, each with the impact declared for it.

## Let Discord keep up

The Discord integration edits its message as the incident develops rather than
posting a new one each time. A channel following a two-hour incident ends up with
one message that reads as the current state, not eleven that have to be read in
order.

See [Notifications](/guide/notifications).

![How an announced maintenance window and the per-component availability reach the public page](/screenshots/en/status-page-public-components.jpg)

## Do it from a script

Everything above is available over the API with the `incidents:write` and
`maintenances:write` scopes — which is what makes it possible to open an incident
from the same pipeline that noticed the problem. See
[Incidents](/api/incidents) and [Maintenances](/api/maintenances).
