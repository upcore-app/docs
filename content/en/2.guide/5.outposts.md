An **outpost** is a small Go service, in its own repository, that runs the same
checks upcore does — from a different network, a different country, a different
continent. upcore is the client: it asks the probe, the probe answers.

::outpost-mark
Its own binary on its own release cadence — deployed where you need a second
opinion, and idle until upcore asks.
::

## Add one

::steps{level="3"}

### Mint a setup key

Under **Outposts**, upcore generates a one-time key — `ost_<prefix>_<secret>`,
valid 24 hours, single use, stored hashed — and renders it inside a deploy
command.

### Deploy the probe

Pick the form that fits the host: Docker Compose, `docker run`, a Kubernetes
manifest, or the install script, which installs a **binary as a systemd service**
so the probe host needs no Docker at all.

### Let it enrol itself

The probe presents the setup key to `POST /api/outposts/enroll` — the one
unauthenticated write in the whole API, because the probe has no session and no
key upcore knows yet. The row is created.

### Watch it verify

upcore calls the probe back with the key it was just handed, trying every address
the probe could be at, repeatedly, for about twenty seconds. A container that has
just started is a moving target.

::

If the callback succeeds the outpost is **verified**. If it does not, the row is
written anyway with the reason recorded, and upcore keeps retrying from the
monitor runner.

::warning
An unverified outpost is inert: visible, retried, and never dispatched to. A
probe upcore cannot reach can never become a location that silently never votes.
::

## Understand the candidate addresses

upcore tries, in this order:

1. An explicit `OUTPOST_PUBLIC_URL` the probe was configured with.
2. The globally routable interface addresses the probe reported about itself.
3. The source address of the enrollment request.

The source address is last because it is the only entry that can belong to
something else — behind a CDN or reverse proxy it is the edge that forwarded the
enrollment, not the probe. Addresses the probe reports are re-filtered for public
routability and capped: the enrollment body is unauthenticated, and every entry
costs a connection attempt.

## Let the locations vote

A monitor says who checks it and how the answers are folded together:

| `check_strategy` | |
| --- | --- |
| `local` | The upcore process itself. The default. |
| `outposts` | The assigned probes only. |
| `both` | Both. |

| `outpost_policy` | Down when… |
| --- | --- |
| `any` | any location says down |
| `majority` | more than half say down |
| `all` | every location says down |

The result is folded into the **one** heartbeat everything else reads, so the
status pages, the SLA and the notifications never learn that more than one
location was involved. The raw per-location verdicts go to a table of their own,
linked to the heartbeat they were folded into — which is what lets the admin UI
answer "what did each location say for *this* ping", not only "what did each
location say last".

Two rules that are easy to get wrong:

::u-page-grid
  :::u-page-card
  ---
  icon: i-lucide-circle-slash
  variant: subtle
  ---
  #title
  A location that could not be reached does not vote

  #description
  A dead probe says nothing about the monitor. Counting it as a failure would
  turn every outpost outage into a false alarm. If *no* location reported, the
  round writes nothing at all — "nobody could be asked" is not "it is down".
  :::

  :::u-page-card
  ---
  icon: i-lucide-life-buoy
  variant: subtle
  ---
  #title
  A monitor whose outposts are all gone falls back to the central check

  #description
  Silently stopping to monitor something is the one outcome that must not happen.
  What a monitor can lose is a location, never its check.
  :::
::

## Know the wire protocol

Three endpoints on the probe, all JSON:

| Endpoint | |
| --- | --- |
| `GET /healthz` | Unauthenticated liveness. |
| `GET /v1/info` | Who and where it is. Prefills the admin form, and every later identification refreshes location, provider, country and version. |
| `POST /v1/checks` | `{ checks: [...] }` → `{ results: [...] }`. |

::note
A field the probe reports empty is left alone rather than cleared, so an admin's
own wording for a location survives a probe that names nothing.
::

**One request per outpost per round, not one per monitor.** The runner collects
everything that is due, groups it by outpost and sends each probe a single batch.
Three outposts and forty monitors is three requests, not a hundred and twenty.

## Use shared outposts on Cloud

Self-hosted, every outpost is one you run — there is nothing to share and no
limit on how many there are.

On [upcore Cloud](/cloud/overview) your plan hands out **shared** probes on top
of that: locations onesrv runs, picked on a monitor like any other. Only the
outposts you enroll yourself count against your plan's outpost limit, because
those are the ones you provision and pay for.

If a plan change takes a shared location away, the assignments that depended on
it are removed right there rather than on the next check round. A monitor loses a
location, never its check.

### See the locations a plan would add

A probe your plan does not include is not simply missing from the monitor form —
it is listed there, greyed out, with a lock and the tiers it comes with. A
location that is absent reads as a location that does not exist, which is the
wrong thing to learn about a fleet somebody else is running.

It is a label and not a checkbox: it cannot be picked, and a disabled checkbox
that never ticks reads as a bug rather than as a price. Nothing about the list
grants anything either — a monitor write still asserts against the locations the
organization may actually use, so the worst a client can do with it is draw it.

The list is empty on every self-hosted instance, and inside the operator
organization.

::note
Tags, not a list of ids, are what share a probe: the operator brings up a box,
tags it `eu`, and every tier carrying that tag gains it without a single tier
being edited. Retiring the box removes it from every plan at once. Only the
operator's own outposts can be tagged — a tag on a tenant's own probe would mean
nothing, so it is refused rather than stored and ignored.
::
