## Assign a role

There are two, and the difference is what they may break:

| Role | May |
| --- | --- |
| **admin** | Everything — monitors, status pages, users, API keys, settings. |
| **editor** | Incidents and maintenance windows. Read-only on monitors and status pages. |

`editor` is the role for whoever is on call: they can tell people what is
happening without being able to change what is watched.

::note
An account created by self-registration is an `editor`. Promote it under
**Users** if it should be more. Handing admin to whoever finds the registration
URL is not a default.
::

## Issue an API key

Under **API keys**, admin only. A key looks like `upc_<prefix>_<secret>` and is
shown **exactly once** — only `sha256(secret)` is stored, so a lost key is
replaced, not recovered.

A key carries:

- **Scopes** — `monitors:read`, `monitors:write`, `incidents:read`,
  `incidents:write`, `maintenances:read`, `maintenances:write`. A `:write` scope
  implies its `:read`.
- **An optional expiry date.**
- **An optional CIDR binding** — a list of networks the key may be used from.

Key management is deliberately not reachable through `/api/v1`: a key can never
create, modify or read another key.

See [API authentication](/api/authentication) for the details, including what
`NUXT_TRUST_PROXY` has to do with CIDR bindings.

## Connect single sign-on

upcore speaks OpenID Connect: the authorization code flow with PKCE against the
provider's discovery document, verifying the ID token against its JWKS. The
implementation is dependency-free against `node:crypto`.

Configuration lives in the **database**, not in the environment, so it is edited
in the SSO tab under **Settings** — including the mapping from provider groups to
upcore roles. The redirect URI is derived from the request and honours
`NUXT_TRUST_PROXY`.

::warning
SSO auto-provisioning is the one path that adds members without anybody deciding
to. On upcore Cloud it counts against your plan's member limit like every other
way in.
::

## Understand sessions

Session cookies are **host-only**: no `Domain` attribute is set, on purpose. On
upcore Cloud a cookie for `.upcore.app` would be sent to every organization
hosted there, so one login would be a login everywhere.

Crossing hosts is therefore an explicit handoff — the organization picker mints a
single-use, two-minute token and the target host exchanges it for a session of
its own.

The session carries no role. The role is resolved per request against the organization
that was addressed, so a session replayed against another one finds no
membership and is refused whatever it is elsewhere.

### Switch organization

An account can belong to more than one. On upcore Cloud the sidebar footer names
the organization you are in and opens the others in a popover — it is not
rendered self-hosted, and not for an account with a single membership, because a
menu with one entry leads back to where you already are.

The switcher **cannot enter an organization itself**. Sessions are host-scoped and
minting a handoff from inside a tenant is refused on purpose: that refusal is what
keeps a foothold in one organization from becoming a session in every other one
the account can reach. An entry therefore links to the picker on the main domain
naming the target, and the picker enters it on arrival — where membership is
re-read server-side, so the named organization is a preselection and never an
authorization.

## Secure the account itself

Roles and keys decide what a session may do. What it takes to *get* a session —
passkeys, an authenticator app, recovery codes, the organization-wide requirement
and the list of signed-in devices — is [Account
security](/guide/account-security).
