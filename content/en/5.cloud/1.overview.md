Not everybody wants a container to look after. **upcore Cloud** is upcore run as
a service by onesrv: you sign up at [go.upcore.app](https://go.upcore.app/register), add a
monitor, and the chapters of this documentation about databases, updates, TLS and
mail relays stop being your problem.

It is the same application the rest of these docs describe — same check types,
same status pages, same API — on infrastructure somebody else keeps running.

## Start free

Signing up puts you on the free plan. No card, no trial clock: it is meant to be
used, not to expire. Your organization gets its own address —
`yourname.upcore.app` — and its own data, separate from everybody else's.

When you outgrow it, upgrading is a page in the app. Plans differ in numbers,
not in which features exist:

| What a plan sets | What it decides |
| --- | --- |
| Monitors, status pages, members, notifications, API keys | how many of each you may create |
| Minimum check interval | how often a monitor may check |
| History retention | how far back the graphs and the daily aggregates go |
| Probe locations | which shared outposts you may check from |

The current numbers are on the pricing page and, once you are signed in, under
**Billing**. A limit bounds what you *create*: moving to a smaller plan refuses
the next monitor, it never deletes the ones you already have.

::note
Payment, invoices and plan changes are handled by onesrv. Nothing about billing
exists in a self-hosted instance — see [Cloud or
self-hosted](/cloud/self-hosted-or-cloud).
::

## Use the same documentation

Everything under [Guide](/guide/monitors) and [API](/api/authentication) applies
unchanged: the eight check types, status pages and their branding, incidents and
maintenance, the nine notification channels, embeds and badges, roles and API
scopes.

What does not apply is the operational half — [installation](/getting-started/installation),
[configuration](/getting-started/configuration), [databases](/operations/databases),
[scaling](/operations/scaling), [mail](/operations/mail) and
[migrations](/operations/migrations-and-updates). Those pages describe the
instance itself, and on Cloud the instance is not yours to configure.

## Bring your own outposts

Shared probe locations are not the only ones you can use. An outpost is a small
container you run yourself, and a Cloud organization can enroll its own — which
is how you check something that is only reachable from inside your own network.
Shared locations come with the plan; your own count against the plan's outpost
limit, because you are the one running them.

See [Outposts](/guide/outposts) for what a probe is and how enrolment works.
