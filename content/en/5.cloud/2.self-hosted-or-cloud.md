The two are the same software. Nothing in the guide is written for one of them
only, and no feature is held back from the version you run yourself.

What differs is everything around the application.

| | Self-hosted | upcore Cloud |
| --- | --- | --- |
| Operated by | you | onesrv |
| Updates | `docker compose pull && docker compose up -d`, when you decide | rolled out for you |
| Database | SQLite file or your PostgreSQL | included |
| Backups | yours to make and to test | included |
| Domain and TLS | your reverse proxy | included |
| Mail | only if you configure an SMTP relay | included |
| Limits | none — nothing is metered | set by your plan |
| Cost | your infrastructure | free to start, paid plans above it |
| Probe locations | every outpost is one you run | shared ones come with the plan; your own on top |
| Reaches a private network | directly, if you run it in there | through an outpost you run in there |

## Pick self-hosted when

- The data must stay on infrastructure you control, and that is the requirement
  rather than a preference.
- You want no limits at all: monitors, retention and check intervals bounded by
  the machine and nothing else.
- You already run containers, and one more against a SQLite file is not work you
  will notice.
- You want to read, patch or fork the source. It is
  [source-available](https://github.com/upcore-app/upcore/blob/main/LICENSE.md),
  and self-hosting is the point of it.

[Installation](/getting-started/installation) gets you there in four commands.

## Pick Cloud when

- Monitoring is supposed to be the thing you *have*, not a thing you run. A
  monitoring system that is down because you forgot to renew a certificate has
  failed at its one job.
- You want checks from several locations without provisioning a box in each.
- Mail should work on day one, without finding a relay that will send for you.
- Nobody on the team wants to own a database, its backups, and the restore
  nobody has tried.

[Sign up at go.upcore.app](https://go.upcore.app) — the free plan needs no card.

## Change your mind later

Both directions are possible, but neither is a button. Monitors, incidents and
maintenance windows are readable and creatable over
[the API](/api/authentication), so moving them is a script rather than an export
format — and the same script works in either direction, because both sides speak
the same `/api/v1`.

Heartbeat history does not travel: it belongs to the instance that recorded it.
Plan a move for when you can afford to start the graphs again.
