upcore is configured entirely through the environment. `.env.example` in the
repository documents every variable in place; this page is the same set,
organised by what it decides.

::note
Settings that belong to the *organization* rather than to the deployment — retention,
status page branding, SSO, notification channels — live in the database and are
edited in the admin UI, not here.
::

![The instance settings in the admin UI: start page, interface language and data retention](/screenshots/en/settings.jpg)

## Set what is required

```ini [.env]
NUXT_SESSION_PASSWORD=
```

The key `nuxt-auth-utils` encrypts the session cookies with. At least 32
characters, and changing it later invalidates every login.

```bash [Terminal]
openssl rand -base64 32
```

## Choose a database

| Variable | Default | |
| --- | --- | --- |
| `DB_DRIVER` | `sqlite` | `sqlite` or `postgres`. Both are fully implemented. |
| `DATABASE_URL` | — | Required for `postgres`. A password with special characters must be URL-encoded. |
| `UPCORE_DATA_DIR` | `.data` | Where the SQLite file (`<dir>/upcore.db`) and uploaded icons (`<dir>/icons`) live. `/data` in the container, from a volume. |
| `DB_FILE` | — | Overrides the SQLite path if the file should not sit under `UPCORE_DATA_DIR`. |

In the Docker stack with the Postgres override, `DATABASE_URL` is built from
`POSTGRES_USER`, `POSTGRES_PASSWORD` and `POSTGRES_DB` and does not need setting
here.

::warning
Switching `DB_DRIVER` does **not** move any data — the other database starts
empty.
::

See [Databases](/operations/databases) for what the two-driver rule means in
practice.

## Publish the app

| Variable | Default | |
| --- | --- | --- |
| `APP_BIND` | `127.0.0.1` | Address the container publishes on. |
| `APP_PORT` | `3000` | Port. |
| `NUXT_PUBLIC_APP_URL` | — | Absolute base URL of this instance. Used for the links in Discord messages; without it those messages carry no link. |
| `UPCORE_IMAGE` / `UPCORE_TAG` | GHCR / `latest` | Which image the stack runs. |

`127.0.0.1` is deliberate: TLS belongs to a reverse proxy in front of upcore. On
`0.0.0.0` the same plaintext HTTP — and every login over it — would be on the
network.

## Decide who may sign up

```ini [.env]
NUXT_REGISTRATION_ENABLED=false
```

Off by default. `/register` does not exist and `/api/auth/register` answers
`403`: an instance that was never meant to be public must not become public by
being upgraded.

Registering joins the one organization this instance is. The new member is an
`editor`; promote them under `/admin/users`. Handing admin to whoever finds the
URL is not a default.

Registration never runs before setup: with no account at all, `/login` shows the
first-admin form and that is what creates it.

## Send mail

Empty `NUXT_SMTP_HOST` — the default — means upcore sends **no mail at all**: no
address confirmation, no password reset, no welcome message, and
`/api/auth/password-reset` answers `404`.

| Variable | Default | |
| --- | --- | --- |
| `NUXT_SMTP_HOST` | — | The relay. Empty = no mail. |
| `NUXT_SMTP_PORT` | `587` | `587` speaks STARTTLS, `465` is implicit TLS and is recognised from the port alone. |
| `NUXT_SMTP_SECURE` | `false` | Force implicit TLS on a non-standard port. Almost never needed. |
| `NUXT_SMTP_REQUIRE_TLS` | `true` | Refuse to send over a connection that could not be encrypted. |
| `NUXT_SMTP_USER` / `NUXT_SMTP_PASSWORD` | — | Empty for a local MTA that wants no authentication. |
| `NUXT_SMTP_FROM` | `NUXT_SMTP_USER` | The From address, when the user is one. |
| `NUXT_SMTP_FROM_NAME` | `upcore` | The name in front of it. |
| `NUXT_SMTP_REPLY_TO` | — | Only worth setting if somebody reads the replies. |
| `NUXT_SMTP_REJECT_UNAUTHORIZED` | `true` | Verify the relay's certificate. |
| `NUXT_EMAIL_VERIFICATION` | `true` | Whether a self-registered account must confirm its address before it can log in. |

::note
`NUXT_EMAIL_VERIFICATION` only ever decides anything where a relay exists. That
is what makes verification safe to *require*: an instance that cannot send the
confirming mail never creates an account waiting for one.
::

See [Mail](/operations/mail) for the full flow.

## Sit behind a proxy

```ini [.env]
NUXT_TRUST_PROXY=false
```

Reads the client IP from `x-forwarded-for`. Only enable it behind a proxy **you
control**: the API key CIDR binding relies on this, and an untrusted proxy lets a
caller pick their own source address, which makes the binding worthless.

## Run more than one container

```ini [.env]
NUXT_SCHEDULER=auto
```

Who runs the background schedules: the monitor checks, the outpost verification
retries, the retention pass, the Discord sync.

| Value | |
| --- | --- |
| `auto` | The default, and right for every deployment. The schedules are leased in the database, so exactly one process runs them however many there are. |
| `off` | This process serves HTTP and nothing else. |
| `on` | This process always runs them, without asking. |

`off`/`on` are for splitting the roles instead of electing one: `off` on the web
replicas, `on` on a single dedicated runner service. `on` checks nothing, so two
processes carrying it duplicate every check.

See [Running more than one container](/operations/scaling).

## Set the timezone

```ini [.env]
TZ=Europe/Berlin
```

Storage is always UTC; this only affects log timestamps and what the runner
reports.
