## Check the prerequisites

- **Docker** with the Compose plugin. That is the whole runtime requirement — no
  database server, no Node on the host, no build tooling.
- **A reverse proxy** in front of the app for TLS. upcore binds to
  `127.0.0.1:3000` on purpose; the same plaintext HTTP on `0.0.0.0` would put
  every login on the network.
- **`openssl`**, or any other way to produce 32 random characters.

## Run it with Docker

::steps{level="3"}

### Clone the repository

```bash [Terminal]
git clone https://github.com/upcore-app/upcore.git
cd upcore
```

### Create the environment file

```bash [Terminal]
cp .env.example .env
```

Every variable in that file is documented in place. Exactly one has to be filled
in before the stack will start.

### Set the session key

`NUXT_SESSION_PASSWORD` encrypts the session cookies and must be at least 32
characters. Changing it later invalidates every login.

```bash [Terminal]
openssl rand -base64 32
```

Paste the result into `.env`:

```ini [.env]
NUXT_SESSION_PASSWORD=xJ4k…
```

### Start the stack

```bash [Terminal]
docker compose up -d
```

That is the whole deployment: SQLite in a volume, no database server to run.

::

Open `http://127.0.0.1:3000` — through your proxy, the address you gave it — and
the first run asks you to create the admin account. There is no default password
and no seeded user: with no account at all, `/login` shows the first-admin form,
and that form is what creates it.

::tip
`GET /api/health` reports whether the database answers **and** whether migrations
have run. It is what the container healthcheck calls, and it is public — point
your own monitoring at it.
::

## Use PostgreSQL instead

Add the override file and set a password in `.env`:

```ini [.env]
POSTGRES_PASSWORD=…
```

```bash [Terminal]
openssl rand -hex 24
```

```bash [Terminal]
docker compose -f docker-compose.yml -f docker-compose.postgres.yml up -d
```

::warning
Switching `DB_DRIVER` does not move any data. The other database starts empty.
Decide before you have rows worth keeping, or migrate them yourself.
::

An alphanumeric password saves you an encoding step: the value ends up inside a
connection URL, where special characters have to be percent-encoded.

## Pin an image

`.github/workflows/docker.yml` pushes two images to GHCR **when a release is
published**:

| Image | What it is |
| --- | --- |
| `ghcr.io/upcore-app/upcore:<tag>` | the app — the Nitro bundle on Node, no source, no build tooling |
| `ghcr.io/upcore-app/upcore:<tag>-migrate` | the migration runner — the two database drivers and the SQL files |

They are always pushed together: a `migrate` image older than the app would apply
a schema the app does not expect.

Releasing `v1.2.3` publishes `1.2.3`, `1.2` and `1`, so a deployment can pin how
far it follows. `latest` moves only for a full release, never for a pre-release
and never because something got merged.

```ini [.env]
UPCORE_TAG=1.2
```

`docker compose build` builds both images from your checkout instead.

## Run it from source

For development, or to run against a checkout rather than an image.

::steps{level="3"}

### Install dependencies

`bun.lock` is the lockfile — there is no `package-lock.json`, and adding one back
would give the image and your machine two different dependency trees.

```bash [Terminal]
bun install
```

### Configure

```bash [Terminal]
cp .env.example .env   # then set NUXT_SESSION_PASSWORD
```

### Start the dev server

```bash [Terminal]
bun run dev
```

This applies migrations first, then starts Nuxt on `http://localhost:3000`.

::

::note{title="bun installs, node runs"}
bun is the package manager only. The Nuxt build, the migration runner and the
shipped server all run under node — that is why `better-sqlite3` resolves the
prebuilt binary for node's ABI, and why the Dockerfile is based on `node:22-slim`
with the bun binary copied in.
::

### Work against PostgreSQL locally

```bash [Terminal]
docker run -d --name upcore-pg -p 5432:5432 \
  -e POSTGRES_USER=upcore -e POSTGRES_PASSWORD=upcore -e POSTGRES_DB=upcore \
  postgres:17-alpine

DB_DRIVER=postgres DATABASE_URL=postgres://upcore:upcore@localhost:5432/upcore bun run dev
```

## Update an instance

```bash [Terminal]
docker compose pull && docker compose up -d
```

The `migrate` service runs first, brings the schema up to date and exits; the app
starts only once it has finished with exit code 0. If it fails, that is a real
fault — a broken migration or an unreachable database — and the app deliberately
does not start at all rather than run against a schema that does not match the
code:

```bash [Terminal]
docker compose logs migrate
```

::note
An existing SQLite database from before migrations existed is adopted on the
first run: its missing columns are added, then it is recorded as migrated.
::
