`DB_DRIVER` selects `sqlite` (the default) or `postgres`. Neither is the real one
with the other bolted on.

## Start on SQLite

One file, no server, no setup. It lives at `<UPCORE_DATA_DIR>/upcore.db` —
`/data/upcore.db` in the container, from a volume, so it survives a deploy.
Uploaded status page icons sit next to it in `<UPCORE_DATA_DIR>/icons`.

This is the right choice for a single container, which is most deployments.

```ini [.env]
DB_DRIVER=sqlite
UPCORE_DATA_DIR=/data
```

Back it up by copying the file while the app is stopped, or with `sqlite3
upcore.db ".backup"` while it runs.

## Move to PostgreSQL

For a shared or replicated deployment.

```ini [.env]
DB_DRIVER=postgres
DATABASE_URL=postgres://upcore:secret@db:5432/upcore
```

In the Docker stack, add the override file and set `POSTGRES_PASSWORD`; the URL
is built for you:

```bash [Terminal]
docker compose -f docker-compose.yml -f docker-compose.postgres.yml up -d
```

::warning
Switching `DB_DRIVER` does **not** move any data. The new database starts empty.
There is no built-in migration between the two; export and import yourself if you
have rows worth keeping.
::

A password with special characters must be URL-encoded — the value is part of a
URL. `openssl rand -hex 24` gives you one that needs no encoding.

## Know what "both are supported" costs

If you contribute code, this is the part that constrains you. Every rule below
exists because a query written for one driver silently misbehaves on the other.

::u-page-grid
  :::u-page-card
  ---
  icon: i-lucide-timer
  variant: subtle
  ---
  #title
  Every query is awaited

  #description
  `better-sqlite3` is synchronous and Drizzle exposes that as `.all()` /
  `.get()` / `.run()`. There is no such thing for Postgres — and a Drizzle query
  builder that is never awaited never runs, which no type error catches. Those
  three methods appear nowhere in `server/`.
  :::

  :::u-page-card
  ---
  icon: i-lucide-copy
  variant: subtle
  ---
  #title
  Every table exists twice

  #description
  `schema.sqlite.ts` and `schema.pg.ts`. `schema.ts` picks the pair matching
  `DB_DRIVER` and is the only one anything else may import. A column added to one
  twin must be added to the other; enums live once, in `constants.ts`.
  :::

  :::u-page-card
  ---
  icon: i-lucide-file-code
  variant: subtle
  ---
  #title
  The SQL has to be portable

  #description
  No `datetime('now')`, `date('now')`, `strftime` or the two-argument `MAX` —
  those are SQLite's. Compute time bounds in JavaScript and pass them as values.
  :::

  :::u-page-card
  ---
  icon: i-lucide-sigma
  variant: subtle
  ---
  #title
  Aggregates need a cast

  #description
  Postgres types `COUNT`/`SUM` as bigint and `AVG` as numeric, and node-postgres
  returns both as **strings**. Write `CAST(COUNT(*) AS INTEGER)` and
  `CAST(AVG(…) AS DOUBLE PRECISION)`.
  :::
::

Both twins deliberately store timestamps as `TEXT` and booleans as `INTEGER` 0/1,
so a row read from either driver is indistinguishable to the code above it.

## Read a timestamp

Timestamps are stored as `'YYYY-MM-DD HH:MM:SS'` in UTC and sort as strings. The
format carries no zone, so parsing one means saying "UTC" explicitly — and the
API hands out exactly the same strings the app parses.

## Check that it answers

```bash [Terminal]
curl -s https://status.example.com/api/health
```

`GET /api/health` reports whether the database answers **and** whether migrations
have run. It is what the container healthcheck calls, and it is public.
