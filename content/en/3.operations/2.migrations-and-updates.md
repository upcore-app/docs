**The application never creates its schema.** A separate runner applies the SQL
files in `server/db/migrations/<driver>/` in order, each exactly once, recorded in
a `schema_migrations` table.

## Update an instance

```bash [Terminal]
docker compose pull && docker compose up -d
```

That is the whole procedure. The `migrate` service runs on every `up`, brings the
schema up to date and exits; the app container starts only once it has finished
with exit code 0.

The run is unattended and idempotent — running it twice applies nothing twice.

## Read a failure

If migration fails, that is a real fault: a broken migration, or an unreachable
database. The app deliberately **does not start at all** rather than run against a
schema that does not match the code.

```bash [Terminal]
docker compose logs migrate
```

::note
An existing SQLite database from before migrations existed is adopted on the
first run: its missing columns are added, then it is recorded as migrated.
::

## Run it by hand

```bash [Terminal]
bun run db:migrate
```

Applies migrations to whatever `DB_DRIVER` and `DATABASE_URL` currently name.
`bun run dev` does this for you before starting.

## Keep the images in step

Two images are published together under the same tag:

| Image | |
| --- | --- |
| `ghcr.io/upcore-app/upcore:<tag>` | the app |
| `ghcr.io/upcore-app/upcore:<tag>-migrate` | the migration runner |

::warning
Never pull them separately. A `migrate` image older than the app applies a schema
the app does not expect.
::

Images are built **only when a GitHub release is published**, plus a manual
dispatch. A push to a branch runs the checks — OpenAPI spec current, migrations
apply to both drivers and re-apply idempotently — and stops there. `latest` never
moves because something got merged.

## Write a migration

If you are contributing a schema change:

::steps{level="3"}

### Add the SQL twice

A new numbered `.sql` file in **both** `server/db/migrations/sqlite/` and
`server/db/migrations/postgres/`.

### Add the column twice

The matching column in both schema twins, `schema.sqlite.ts` and `schema.pg.ts`.

### Never edit an applied migration

It will not run again. Add a new file instead.

::

::note
The runner is plain JavaScript and repeats the environment rules from
`server/db/config.ts` rather than importing them — the migration image carries no
TypeScript loader. Change one, change the other.
::

## Delete an organization safely

Nothing cascades from the organization row itself: `organization_id` was
introduced as a plain foreign key. `deleteOrganization()` empties the root tables
one by one and lets the database cascade everything below them.

A new **root** table missing from that list makes deleting an organization fail on a
foreign key — or worse, leave its rows behind.
