An upcore instance holds the addresses of your internal services, the credentials
of your notification channels, and the accounts of everyone who can change them.

## Harden a deployment

The defaults are safe for the intended shape — one container behind a reverse
proxy you control. These are the decisions that are yours.

::steps{level="3"}

### Set a real session key

At least 32 characters, from an actual random source. Never reuse it across
instances, never commit it.

```bash [Terminal]
openssl rand -base64 32
```

### Terminate TLS in front of upcore

The container publishes on `127.0.0.1:3000` deliberately. Binding `APP_BIND` to
`0.0.0.0` puts plaintext HTTP — and every login over it — on the network.

### Trust only a proxy you control

`NUXT_TRUST_PROXY=true` makes the client IP come from `x-forwarded-for`. Behind
an untrusted proxy — or with none at all — a caller picks their own source
address and the CIDR binding on every API key becomes worthless.

### Rate-limit at the proxy

upcore does not rate-limit logins or API requests. Put that in front of it, along
with any IP allowlist for `/admin` and `/api`, if the instance is reachable from
the internet.

### Scope API keys narrowly

Grant the smallest scope set that works, set an expiry, and bind the key to a
CIDR range when the caller has a fixed address. Rotate by creating the
replacement, switching the caller over, then deleting the old one.

### Back up the data directory

`UPCORE_DATA_DIR` — or your Postgres database. It holds the monitoring history,
the uploaded icons and the API key hashes.

### Restrict who is an admin

Admins can set custom CSS on public status pages and configure outbound webhook
targets. Both are legitimate features and both are powerful.

### Require a second factor

**Settings → Two-factor authentication.** upcore does not rate-limit logins, so a
password on its own is only as good as the password. Enrol your own passkey or
authenticator app and sign in with it *before* turning the requirement on — it
applies to you as well. See [Account security](/guide/account-security).

::

::warning
**A status page is public.** Anything attached to one — monitor names, incident
text, footer links — is visible to everyone who has the slug. Keep internal
hostnames out of monitor names that appear on a public page.
::

## Know what upcore does itself

| | |
| --- | --- |
| **Sessions** | Cookies sealed with `NUXT_SESSION_PASSWORD`. Passwords stored hashed, never in plain text. Every session is a row of its own, so signing a device out takes effect on its next request rather than at its next login — see [Account security](/guide/account-security). |
| **Second factor** | Passkeys (WebAuthn) and TOTP with single-use recovery codes, of which only hashes are stored. An organization can require one from every member, and the last factor cannot be dropped while any organization the account belongs to still requires it. A password login that needs a code holds the half-finished state in a sealed five-minute note, never in a session. |
| **Roles** | The admin API is guarded by middleware. Editors may write incidents and maintenance, and read — but not write — monitors and status pages. |
| **API keys** | Only `sha256(secret)` is stored. Checked in order: key exists → secret matches → active and unexpired → source inside the CIDR binding → holds the required scope. An unknown prefix and a wrong secret return the same message. |
| **Key management** | Not exposed through `/api/v1`, so a leaked key cannot mint another one or widen its own scopes. |
| **API separation** | `/api/v1` is deliberately absent from the session guard's prefix list and authenticates on its own. |
| **Uploaded icons** | 512 KB cap, a fixed set of image types, random hex filenames inside `UPCORE_DATA_DIR`, served with `Content-Security-Policy: default-src 'none'` so an uploaded SVG cannot run scripts. |
| **Input validation** | Every write endpoint. `/api/v1` with zod schemas that also generate the OpenAPI document; the admin API with explicit validators. |
| **Public by design** | `GET /api/health` reports only whether the database answers and whether migrations have run. `GET /api/v1/openapi.json` describes how to authenticate and contains no instance data. |

## Report a vulnerability

::caution
Do not open a public issue, pull request or discussion for a vulnerability.
::

Report it privately through GitHub: repository → **Security** → **Report a
vulnerability**, or directly at
[github.com/upcore-app/upcore/security/advisories/new](https://github.com/upcore-app/upcore/security/advisories/new).
That opens a private advisory only you and the maintainers can read.

Useful in a report:

- The affected version or commit, and the `DB_DRIVER` in use.
- A minimal reproduction — a request, a sequence of steps, a proof of concept.
- What an attacker gains: which data, whose account, which privilege boundary.
- Whether it needs authentication, and with which role.

### What to expect

| | |
| --- | --- |
| Acknowledgement | within 72 hours |
| Initial assessment | within 7 days — accepted, needs more information, or out of scope |
| Fix | as soon as it is ready; 90 days at the outside |
| Credit | in the advisory and the release notes, unless you would rather not be named |

Test against **your own instance**. Never against an instance you do not operate,
and never against a third party's public status page.

### Know the scope

**In scope** — anything that breaks a boundary: authentication, authorization,
API key handling, injection (SQL, stored XSS on a public page or embed, SSRF
through a monitor target, path traversal in icon handling), leaking configured
secrets, remote code execution, container escape, or writes outside
`UPCORE_DATA_DIR`.

**Out of scope** — findings that require an account you already control to attack
itself (an admin is trusted by design), missing rate limiting or security headers
(see hardening above), scanner output with no demonstrated impact, volumetric
denial of service, and vulnerabilities in a dependency upcore does not reach.

## Follow the fixes

Fixes go onto the latest release; there are no long-lived maintenance branches,
so upgrading to the current release is the supported way to receive one.
Published advisories are listed at
[github.com/upcore-app/upcore/security/advisories](https://github.com/upcore-app/upcore/security/advisories).
