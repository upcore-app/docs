Leave `NUXT_SMTP_HOST` empty — the default — and upcore sends **nothing at all**:
no address confirmation, no password reset, no welcome message. A self-hosted
instance stays exactly as it was until somebody points it at a relay.

That is also what makes address verification safe to *require* where a relay does
exist: an instance that cannot send the confirming mail never creates an account
waiting for one, so nobody is ever locked out by a server you never set up.

## Point it at a relay

```ini [.env]
NUXT_SMTP_HOST=smtp.eu.mailgun.org
NUXT_SMTP_PORT=587
NUXT_SMTP_USER=postmaster@mg.example.com
NUXT_SMTP_PASSWORD=…
NUXT_SMTP_FROM=status@example.com
NUXT_SMTP_FROM_NAME=upcore
```

| | |
| --- | --- |
| `587` | STARTTLS. The default. |
| `465` | Implicit TLS, recognised as such from the port alone. |
| `NUXT_SMTP_SECURE=true` | Forces implicit TLS on some other port. Almost never needed. |

`NUXT_SMTP_FROM` defaults to `NUXT_SMTP_USER` when that is an address, which is
what most relays require anyway.

## Keep it encrypted

```ini [.env]
NUXT_SMTP_REQUIRE_TLS=true
NUXT_SMTP_REJECT_UNAUTHORIZED=true
```

Both default to on.

::caution
Turn `NUXT_SMTP_REQUIRE_TLS` off only for a relay on localhost that offers no
STARTTLS. With it off, the credentials above go over the wire in the clear.
::

Turn `NUXT_SMTP_REJECT_UNAUTHORIZED` off only for a private relay whose
self-signed certificate you know.

## Decide whether addresses are confirmed

```ini [.env]
NUXT_EMAIL_VERIFICATION=true
```

On by default, and only ever in effect where a relay is configured.

With it on, a self-registered account is refused at the login until the link in
the confirmation mail has been opened, and an account that never confirms is
deleted after 30 days — on upcore Cloud together with the organization it created
and nobody else ever joined.

::note
That deletion is why the flag exists at all: an instance that hands out
registrations to people it already knows may not want the gate. Set it to `false`
and registrations are open immediately, nothing is deleted for being unconfirmed,
and the welcome mail moves to the registration.
::

Everything else is unaffected. An account created by an admin, by the operator or
by an identity provider is confirmed by construction — somebody who was already
trusted decided it exists — and the password reset works either way.

## Know what gets sent

| Mail | When |
| --- | --- |
| Address confirmation | A self-registration, where verification is on. |
| Welcome | After confirming — or at registration, where verification is off. |
| Password reset | `/api/auth/password-reset`, which answers `404` with no relay. |

Mail is written in the language the person was reading when it was triggered.
