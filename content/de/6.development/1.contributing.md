Issues und Pull Requests sind willkommen. Was folgt, ist das, worauf ein Reviewer
schaut.

## Die Befehle kennen

```bash [Terminal]
bun install        # nach einem Pull, der package.json geändert hat
bun run dev        # migrieren, dann Dev-Server
bun run build      # Produktions-Build (.output)
bun run db:migrate # Migrationen auf die konfigurierte Datenbank anwenden
bun run openapi    # openapi.json neu erzeugen — nach jeder /api/v1-Änderung
bun run typecheck  # vue-tsc -b --noEmit
```

::warning
Das `-b` beim Typecheck ist Pflicht. Ohne es werden Projekt-Referenzen
übersprungen und es wird überhaupt nichts geprüft.
::

## Sich zurechtfinden

```
app/            Nuxt-App — Seiten, Komponenten, Composables (UI-Texte sind Deutsch)
server/api/     Admin-API (Session-authentifiziert) und /api/v1 (API-Keys)
server/db/      zwei Schema-Zwillinge (sqlite/pg) + nummerierte SQL-Migrationen
server/utils/   Validierung, Monitore, API-Key-Handling, CIDR-Matching
shared/         Typen, die Client und Server teilen
scripts/        Migrations-Runner, OpenAPI-Generator
```

## Die Invarianten beachten

Das sind die Dinge, die ein grüner Typecheck nicht fängt.

::steps{level="3"}

### Zwei Datenbanken, eine Codebasis

Jede Query wird awaited, jede Tabelle ist zweimal definiert, das SQL vermeidet
SQLite-eigene Funktionen, und Aggregate werden gecastet, damit Postgres keine
Strings zurückgibt. Lies `server/db/config.ts` und `server/utils/db.ts`, bevor du
`server/db/` anfasst oder eine Query ergänzt.

Siehe [Datenbanken](/de/operations/databases) für die vollständige Liste.

### Der OpenAPI-Vertrag

`openapi.json` ist ein **Build-Artefakt**. Bearbeite es nie von Hand: ändere das
zod-Schema in `server/utils/api/schemas.ts` und den Routen-Eintrag in
`server/utils/api/openapi.ts`, führ `bun run openapi` aus und committe die neu
erzeugte Datei zusammen mit der Codeänderung.

CI prüft, dass sie aktuell ist.

### Die Migrationsregeln

Eine Schemaänderung heißt: eine neue nummerierte `.sql`-Datei in **beiden**
Verzeichnissen, `server/db/migrations/sqlite/` und `.../postgres/`, plus die
passende Spalte in beiden Schema-Zwillingen. Nie eine bereits angewendete
Migration bearbeiten.

CI prüft, dass die Migrationen laufen — und idempotent erneut laufen — gegen SQLite
und PostgreSQL.

### Sprache

Code und Kommentare sind Englisch. Nutzersichtbare Texte laufen über i18n
(`i18n/locales/`), in **beiden** Sprachen, Deutsch und Englisch.

### Neue Hintergrund-Intervalle werden geleast

`acquireLease(job, ttl)` am Anfang des Ticks, dem der Schedule gehört, und
`holdsLease(job)` in den Durchläufen, die daran mitfahren. Ein ungeleaster Timer
läuft einmal pro Replica. Siehe
[Mehr als ein Container](/de/operations/scaling).

### Neue Wurzeltabellen kommen ins Mandanten-Löschen

Von der Organisationszeile selbst kaskadiert nichts. Eine Wurzeltabelle, die in
`deleteOrganization()` fehlt, lässt das Löschen eines Mandanten an einem
Fremdschlüssel scheitern — oder schlimmer, lässt seine Zeilen zurück.

::

## Vor dem Pull Request

```bash [Terminal]
bun run typecheck
bun run openapi:check
```

::note
`bun.lock` ist die Lockdatei. Es gibt keine `package-lock.json`, und eine wieder
hinzuzufügen gäbe Image und Entwicklermaschine zwei verschiedene
Abhängigkeitsbäume. Installiere mit `bun install`, ergänze Pakete mit `bun add`.
::
