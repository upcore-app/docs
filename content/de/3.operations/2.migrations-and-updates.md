**Die Anwendung legt ihr Schema nie selbst an.** Ein eigener Runner wendet die
SQL-Dateien in `server/db/migrations/<driver>/` der Reihe nach an, jede genau
einmal, vermerkt in einer Tabelle `schema_migrations`.

## Eine Instanz aktualisieren

```bash [Terminal]
docker compose pull && docker compose up -d
```

Das ist der ganze Vorgang. Der `migrate`-Service läuft bei jedem `up`, bringt das
Schema auf Stand und beendet sich; der App-Container startet erst, wenn er mit
Exit-Code 0 fertig ist.

Der Lauf ist unbeaufsichtigt und idempotent — ihn zweimal auszuführen wendet
nichts zweimal an.

## Einen Fehler lesen

Schlägt die Migration fehl, ist das ein echter Fehler: eine kaputte Migration oder
eine nicht erreichbare Datenbank. Die App startet bewusst **gar nicht**, statt
gegen ein Schema zu laufen, das nicht zum Code passt.

```bash [Terminal]
docker compose logs migrate
```

::note
Eine bestehende SQLite-Datenbank aus der Zeit vor den Migrationen wird beim ersten
Lauf übernommen: fehlende Spalten werden ergänzt, dann wird sie als migriert
vermerkt.
::

## Sie von Hand ausführen

```bash [Terminal]
bun run db:migrate
```

Wendet die Migrationen auf das an, was `DB_DRIVER` und `DATABASE_URL` gerade
benennen. `bun run dev` erledigt das vor dem Start für dich.

## Die Images im Gleichschritt halten

Zwei Images werden unter demselben Tag zusammen veröffentlicht:

| Image | |
| --- | --- |
| `ghcr.io/upcore-app/upcore:<tag>` | die App |
| `ghcr.io/upcore-app/upcore:<tag>-migrate` | der Migrations-Runner |

::warning
Zieh sie nie getrennt. Ein `migrate`-Image, das älter ist als die App, legt ein
Schema an, das die App nicht erwartet.
::

Images werden **nur gebaut, wenn ein GitHub-Release veröffentlicht wird**, plus per
manuellem Dispatch. Ein Push auf einen Branch führt die Checks aus — OpenAPI-Spec
aktuell, Migrationen laufen auf beiden Treibern und wiederholen sich idempotent —
und hört dort auf. `latest` bewegt sich nie, weil etwas gemerged wurde.

## Eine Migration schreiben

Wenn du eine Schemaänderung beiträgst:

::steps{level="3"}

### Das SQL zweimal ergänzen

Eine neue nummerierte `.sql`-Datei in **beiden** Verzeichnissen,
`server/db/migrations/sqlite/` und `server/db/migrations/postgres/`.

### Die Spalte zweimal ergänzen

Die passende Spalte in beiden Schema-Zwillingen, `schema.sqlite.ts` und
`schema.pg.ts`.

### Nie eine angewendete Migration bearbeiten

Sie läuft nicht noch einmal. Leg stattdessen eine neue Datei an.

::

::note
Der Runner ist einfaches JavaScript und wiederholt die Umgebungsregeln aus
`server/db/config.ts`, statt sie zu importieren — das Migrations-Image bringt
keinen TypeScript-Loader mit. Änderst du das eine, ändere das andere.
::

## Eine Organisation sicher löschen

Von der Organisationszeile selbst kaskadiert nichts: `organization_id` wurde als
einfacher Fremdschlüssel eingeführt. `deleteOrganization()` leert die
Wurzeltabellen eine nach der anderen und lässt die Datenbank alles darunter
kaskadieren.

Eine neue **Wurzeltabelle**, die in dieser Liste fehlt, lässt das Löschen einer
Organisation an einem Fremdschlüssel scheitern — oder schlimmer, lässt seine Zeilen
zurück.
