Eine upcore-Instanz hält die Adressen deiner internen Dienste, die Zugangsdaten
deiner Benachrichtigungskanäle und die Konten aller, die daran etwas ändern
können.

## Ein Deployment härten

Die Standardwerte sind für die vorgesehene Form sicher — ein Container hinter
einem Reverse-Proxy, den du kontrollierst. Das hier sind die Entscheidungen, die
dir gehören.

::steps{level="3"}

### Einen echten Session-Schlüssel setzen

Mindestens 32 Zeichen, aus einer echten Zufallsquelle. Nie über Instanzen hinweg
wiederverwenden, nie einchecken.

```bash [Terminal]
openssl rand -base64 32
```

### TLS vor upcore terminieren

Der Container veröffentlicht bewusst auf `127.0.0.1:3000`. `APP_BIND` auf
`0.0.0.0` zu binden legt Klartext-HTTP — und jeden Login darüber — ins Netz.

### Nur einem Proxy vertrauen, den du kontrollierst

`NUXT_TRUST_PROXY=true` lässt die Client-IP aus `x-forwarded-for` kommen. Hinter
einem nicht vertrauenswürdigen Proxy — oder ganz ohne — wählt der Aufrufer seine
Quelladresse selbst, und die CIDR-Bindung jedes API-Keys wird wertlos.

### Am Proxy rate-limiten

upcore begrenzt weder Logins noch API-Requests. Setz das davor, zusammen mit einer
IP-Allowlist für `/admin` und `/api`, wenn die Instanz aus dem Internet erreichbar
ist.

### API-Keys eng fassen

Vergib die kleinste Scope-Menge, die funktioniert, setz ein Ablaufdatum und binde
den Key an einen CIDR-Bereich, wenn der Aufrufer eine feste Adresse hat. Rotiere,
indem du den Ersatz anlegst, den Aufrufer umstellst und dann den alten löschst.

### Das Datenverzeichnis sichern

`UPCORE_DATA_DIR` — oder deine Postgres-Datenbank. Dort liegen die
Monitoring-Historie, die hochgeladenen Icons und die API-Key-Hashes.

### Einschränken, wer Admin ist

Admins können eigenes CSS auf öffentliche Statusseiten setzen und ausgehende
Webhook-Ziele konfigurieren. Beides sind legitime Funktionen, und beides ist
mächtig.

### Einen zweiten Faktor verlangen

**Einstellungen → Zwei-Faktor-Authentifizierung.** upcore rate-limitet Logins
nicht, ein Passwort allein ist also nur so gut wie das Passwort. Richte deinen
eigenen Passkey oder deine Authenticator-App ein und melde dich damit an, *bevor*
du die Pflicht einschaltest — sie gilt für dich genauso. Siehe
[Kontosicherheit](/de/guide/account-security).

::

::warning
**Eine Statusseite ist öffentlich.** Alles, was daran hängt — Monitornamen,
Störungstexte, Footer-Links — sieht jeder, der den Slug hat. Halte interne
Hostnamen aus Monitornamen heraus, die auf einer öffentlichen Seite erscheinen.
::

## Wissen, was upcore selbst tut

| | |
| --- | --- |
| **Sessions** | Cookies, versiegelt mit `NUXT_SESSION_PASSWORD`. Passwörter gehasht gespeichert, nie im Klartext. Jede Sitzung ist eine eigene Zeile — ein Gerät abzumelden wirkt deshalb bei dessen nächstem Request und nicht erst bei dessen nächster Anmeldung, siehe [Kontosicherheit](/de/guide/account-security). |
| **Zweiter Faktor** | Passkeys (WebAuthn) und TOTP mit einmal verwendbaren Wiederherstellungscodes, von denen nur Hashes gespeichert werden. Eine Organisation kann ihn von allen Mitgliedern verlangen, und der letzte Faktor lässt sich nicht entfernen, solange irgendeine Organisation des Kontos ihn noch verlangt. Eine Passwort-Anmeldung, die einen Code braucht, hält den halbfertigen Zustand in einer versiegelten Fünf-Minuten-Notiz, nie in einer Sitzung. |
| **Rollen** | Die Admin-API ist durch Middleware geschützt. Editoren dürfen Störungen und Wartungen schreiben und Monitore und Statusseiten lesen — nicht schreiben. |
| **API-Keys** | Gespeichert wird nur `sha256(secret)`. Geprüft wird der Reihe nach: Key existiert → Secret passt → aktiv und nicht abgelaufen → Quelle innerhalb der CIDR-Bindung → hält den nötigen Scope. Ein unbekannter Präfix und ein falsches Secret liefern dieselbe Meldung. |
| **Key-Verwaltung** | Nicht über `/api/v1` erreichbar — ein geleakter Key kann also keinen zweiten erzeugen und seine Scopes nicht erweitern. |
| **API-Trennung** | `/api/v1` fehlt bewusst in der Präfixliste des Session-Guards und authentifiziert selbst. |
| **Hochgeladene Icons** | 512 KB Grenze, feste Menge Bildtypen, zufällige Hex-Dateinamen innerhalb `UPCORE_DATA_DIR`, ausgeliefert mit `Content-Security-Policy: default-src 'none'`, damit ein hochgeladenes SVG keine Skripte ausführen kann. |
| **Eingabevalidierung** | Jeder schreibende Endpunkt. `/api/v1` mit zod-Schemas, die auch das OpenAPI-Dokument erzeugen; die Admin-API mit expliziten Validatoren. |
| **Bewusst öffentlich** | `GET /api/health` meldet nur, ob die Datenbank antwortet und ob Migrationen gelaufen sind. `GET /api/v1/openapi.json` beschreibt, wie man sich authentifiziert, und enthält keine Instanzdaten. |

## Eine Schwachstelle melden

::caution
Öffne für eine Schwachstelle kein öffentliches Issue, keinen Pull Request und keine
Discussion.
::

Melde sie privat über GitHub: Repository → **Security** → **Report a
vulnerability**, oder direkt unter
[github.com/upcore-app/upcore/security/advisories/new](https://github.com/upcore-app/upcore/security/advisories/new).
Das öffnet ein privates Advisory, das nur du und die Maintainer lesen können.

Hilfreich in einer Meldung:

- Die betroffene Version oder der Commit, und der verwendete `DB_DRIVER`.
- Eine minimale Reproduktion — ein Request, eine Schrittfolge, ein Proof of
  Concept.
- Was ein Angreifer gewinnt: welche Daten, wessen Konto, welche Grenze.
- Ob Authentifizierung nötig ist, und mit welcher Rolle.

### Was du erwarten kannst

| | |
| --- | --- |
| Empfangsbestätigung | innerhalb von 72 Stunden |
| Erste Einschätzung | innerhalb von 7 Tagen — angenommen, mehr Infos nötig, oder außerhalb des Umfangs |
| Fix | sobald er fertig ist; höchstens 90 Tage |
| Nennung | im Advisory und den Release Notes, außer du willst das nicht |

Teste gegen **deine eigene Instanz**. Nie gegen eine Instanz, die du nicht
betreibst, und nie gegen die öffentliche Statusseite eines Dritten.

### Den Umfang kennen

**Im Umfang** — alles, was eine Grenze bricht: Authentifizierung, Autorisierung,
Umgang mit API-Keys, Injection (SQL, gespeichertes XSS auf einer öffentlichen
Seite oder in einem Embed, SSRF über ein Monitor-Ziel, Path Traversal bei
Icons), Leaken konfigurierter Geheimnisse, Remote Code Execution,
Container-Ausbruch oder Schreibzugriffe außerhalb von `UPCORE_DATA_DIR`.

**Außerhalb des Umfangs** — Funde, die ein Konto brauchen, das du ohnehin
kontrollierst, um sich selbst anzugreifen (ein Admin ist per Design vertraut),
fehlendes Rate-Limiting oder fehlende Security-Header (siehe Härtung oben),
Scanner-Ausgaben ohne belegte Auswirkung, volumetrische Denial-of-Service-Angriffe
und Schwachstellen in einer Abhängigkeit, die upcore gar nicht erreicht.

## Den Fixes folgen

Fixes gehen ins jeweils neueste Release; es gibt keine langlebigen
Wartungsbranches, das Update auf das aktuelle Release ist also der unterstützte
Weg zu einem Fix. Veröffentlichte Advisories stehen unter
[github.com/upcore-app/upcore/security/advisories](https://github.com/upcore-app/upcore/security/advisories).
