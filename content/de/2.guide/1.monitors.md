Ein Monitor ist eine Sache, deren Zustand du kennen willst. Er trägt einen
Check-Typ, ein Ziel, ein Intervall, ein Timeout und eine Fehlerschwelle und
erzeugt einen Strom von Heartbeats.

## Einen Check-Typ wählen

| Typ | Braucht | Was er tut |
| --- | --- | --- |
| `http` | `target` | Ruft die URL ab und prüft den Statuscode. `target` muss mit `http://` oder `https://` beginnen. |
| `keyword` | `target`, `keyword` | Wie `http`, und der Response-Body muss `keyword` enthalten. |
| `ping` | `target` | ICMP-Echo an einen Hostnamen oder eine IP. |
| `tcp` | `target`, `port` | Öffnet eine TCP-Verbindung. |
| `dns` | `target` | Löst einen Namen auf. `dnsRecordType` ist standardmäßig `A`. |
| `ssl` | `target` | Prüft das Zertifikat. `port` ist standardmäßig `443`. |
| `push` | — | Umgekehrt: der Job ruft upcore an. Bei der Anlage wird ein `pushToken` erzeugt. |
| `group` | `memberIds` | Hat keinen eigenen Check. Aggregiert andere Monitore. |

### Einen HTTP- oder Keyword-Check anlegen

Beide nehmen eine eigene HTTP-Methode und Request-Header — genau das macht sie
gegen einen authentifizierten Health-Endpunkt brauchbar:

```json
{
  "name": "API Gateway",
  "type": "keyword",
  "target": "https://api.example.com/health",
  "keyword": "\"status\":\"ok\"",
  "httpHeaders": [{ "name": "X-Probe", "value": "upcore" }]
}
```

### Einen Push-Monitor anlegen

Ein `push`-Monitor ist für Arbeit, die *hereinruft* — Cron-Läufe, Worker,
Backups. upcore erzeugt ein Token, und der Job pusht darauf, wenn er fertig ist:

```bash [crontab]
0 3 * * * /usr/local/bin/backup.sh && curl -fsS https://status.example.com/api/push/<pushToken>
```

Kommt der Push nicht innerhalb des Intervalls, geht der Monitor auf down. Das ist
der einzige Check-Typ, bei dem Schweigen der Fehler ist.

### Monitore gruppieren

Ein `group`-Monitor aggregiert die Monitore in seiner Mitgliederliste und meldet
einen Zustand für alle. Gruppen lassen sich nicht verschachteln, und sie führen
nie einen eigenen Check aus — es gibt für einen entfernten Standort nichts zu
tun, weshalb eine Gruppe immer lokal geprüft wird.

## Festlegen, wann ein Fehler zählt

Drei Einstellungen pro Monitor, und zusammen entscheiden sie, wie laut ein
Aussetzer ist.

| Einstellung | |
| --- | --- |
| `interval` | Sekunden zwischen den Checks. |
| `timeout` | Wie lange ein einzelner Check dauern darf, bevor er als fehlgeschlagen gilt. |
| `failureThreshold` | Wie viele Fehler in Folge den Monitor auf *down* setzen. |

Fehler unterhalb der Schwelle werden als **pending** festgehalten — Status `2` —
und wecken niemanden. Nichts wird versendet, und die Statusseiten werden nicht
rot.

::note
Ein Monitor mit `failureThreshold: 3` bei 60-Sekunden-Intervall braucht drei
Minuten durchgehenden Ausfall, bevor er gemeldet wird. Erhöhe die Schwelle bei
einem Ziel, das bekanntermaßen flattert; senke sie, wo jede Sekunde zählt.
::

## Ein SLA verfolgen

Ein Monitor kann ein SLA-Ziel tragen — etwa 99,9 % über ein 30-Tage-Fenster — und
upcore verfolgt den erreichten Wert dagegen. Er erscheint am Monitor und auf jeder
Statusseite, die ihn anzeigen soll.

Das Fenster ist gleitend, und der Wert wird aus denselben Heartbeats berechnet,
die alles andere liest.

## Die Heartbeats lesen

`GET /api/v1/monitors/{id}` liefert neben dem Monitor die 50 jüngsten Heartbeats.
Ihr `status` ist:

| Wert | Zustand |
| --- | --- |
| `1` | up |
| `0` | down |
| `2` | pending |

Wie viel Historie aufbewahrt wird, ist eine Einstellung pro Instanz, nicht pro
Monitor. In der [upcore Cloud](/de/cloud/overview) begrenzt dein Tarif sie.

## Von mehr als einem Ort prüfen

Standardmäßig prüft der upcore-Prozess selbst. Zwei Felder ändern das:

| Feld | Werte | |
| --- | --- | --- |
| `check_strategy` | `local`, `outposts`, `both` | Wer den Check ausführt. |
| `outpost_policy` | `any`, `majority`, `all` | Wie die Urteile der Standorte zu einem zusammengefasst werden. |

`push`- und `group`-Monitore sind immer `local`: keiner von beiden beschreibt
Arbeit, die ein entfernter Prozess erledigen könnte. Siehe
[Outposts](/de/guide/outposts).

## Einen Monitor sicher ändern

Ein `PATCH` wird auf den aktuellen Monitor gemergt, und das **Ergebnis** wird als
Ganzes validiert — die Typregeln oben gelten also weiter. Einen Monitor auf `tcp`
umzustellen, ohne einen `port` mitzuschicken, wird abgelehnt statt stillschweigend
übernommen.

Siehe die [API-Referenz](/de/api/monitors).
