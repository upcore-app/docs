## Eine Rolle vergeben

Es gibt zwei, und der Unterschied ist, was sie kaputtmachen können:

| Rolle | Darf |
| --- | --- |
| **admin** | Alles — Monitore, Statusseiten, Benutzer, API-Keys, Einstellungen. |
| **editor** | Störungen und Wartungsfenster. Nur lesen bei Monitoren und Statusseiten. |

`editor` ist die Rolle für die Rufbereitschaft: sie kann sagen, was los ist, ohne
ändern zu können, was überwacht wird.

::note
Ein durch Selbstregistrierung angelegtes Konto ist `editor`. Befördere es unter
**Benutzer**, wenn es mehr sein soll. Admin an jeden zu geben, der die
Registrierungs-URL findet, ist kein Standard.
::

## Einen API-Key ausgeben

Unter **API-Keys**, nur für Admins. Ein Key sieht aus wie `upc_<prefix>_<secret>`
und wird **genau einmal** angezeigt — gespeichert wird nur `sha256(secret)`, ein
verlorener Key wird also ersetzt, nicht wiederhergestellt.

Ein Key trägt:

- **Scopes** — `monitors:read`, `monitors:write`, `incidents:read`,
  `incidents:write`, `maintenances:read`, `maintenances:write`. Ein `:write`-Scope
  schließt sein `:read` ein.
- **Ein optionales Ablaufdatum.**
- **Eine optionale CIDR-Bindung** — eine Liste von Netzen, aus denen der Key
  benutzt werden darf.

Die Key-Verwaltung ist bewusst nicht über `/api/v1` erreichbar: ein Key kann nie
einen anderen anlegen, ändern oder lesen.

Siehe [API-Authentifizierung](/de/api/authentication) für die Details, samt dem,
was `NUXT_TRUST_PROXY` mit CIDR-Bindungen zu tun hat.

## Single Sign-on anbinden

upcore spricht OpenID Connect: den Authorization-Code-Flow mit PKCE gegen das
Discovery-Dokument des Providers, mit Prüfung des ID-Tokens gegen dessen JWKS. Die
Umsetzung kommt ohne Abhängigkeiten aus, direkt gegen `node:crypto`.

Die Konfiguration liegt in der **Datenbank**, nicht in der Umgebung — sie wird
also im SSO-Tab unter **Einstellungen** bearbeitet, samt der Zuordnung von
Provider-Gruppen zu upcore-Rollen. Die Redirect-URI wird aus dem Request abgeleitet
und beachtet `NUXT_TRUST_PROXY`.

::warning
SSO-Auto-Provisioning ist der eine Weg, auf dem Mitglieder hinzukommen, ohne dass
sich jemand dafür entscheidet. In der upcore Cloud zählt es gegen das
Mitgliederlimit deines Tarifs wie jeder andere Weg hinein.
::

## Sessions verstehen

Session-Cookies sind **host-gebunden**: es wird bewusst kein `Domain`-Attribut
gesetzt. In der upcore Cloud würde ein Cookie für `.upcore.app` an jede dort
gehostete Organisation gehen — ein Login wäre ein Login überall.

Der Wechsel zwischen Hosts ist deshalb eine ausdrückliche Übergabe: die
Organisationsauswahl erzeugt ein einmaliges Token mit zwei Minuten Gültigkeit, das
der Ziel-Host gegen eine eigene Session eintauscht.

Die Session trägt keine Rolle. Die Rolle wird pro Request gegen die angesprochene
Organisation aufgelöst — eine gegen eine andere Organisation wiedereingespielte Session
findet also keine Mitgliedschaft und wird abgelehnt, was sie anderswo auch sein
mag.

### Organisation wechseln

Ein Konto kann mehreren angehören. In der upcore Cloud nennt der Fuß der
Seitenleiste die Organisation, in der du bist, und öffnet die anderen in einem
Popover — self-hosted wird er nicht gerendert, und für ein Konto mit einer
einzigen Mitgliedschaft auch nicht: ein Menü mit einem Eintrag führt dorthin
zurück, wo man ohnehin schon ist.

Der Umschalter **betritt eine Organisation nicht selbst**. Sitzungen sind an den
Host gebunden, und eine Übergabe aus einem Mandanten heraus zu erzeugen wird
bewusst abgelehnt: Genau diese Ablehnung verhindert, dass ein Fuß in der Tür einer
Organisation zu einer Sitzung in jeder anderen wird, die das Konto erreichen kann.
Ein Eintrag verlinkt deshalb auf die Auswahl auf der Hauptdomain und benennt das
Ziel; betreten wird es dort beim Ankommen — und die Mitgliedschaft wird
serverseitig neu gelesen. Die benannte Organisation ist also eine Vorauswahl und
nie eine Berechtigung.

## Das Konto selbst absichern

Rollen und Keys entscheiden, was eine Sitzung darf. Was es braucht, um überhaupt
eine zu *bekommen* — Passkeys, Authenticator-App, Wiederherstellungscodes, die
Pflicht für die ganze Organisation und die Liste der angemeldeten Geräte — steht
unter [Kontosicherheit](/de/guide/account-security).
