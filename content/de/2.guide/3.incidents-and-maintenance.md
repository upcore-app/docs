Ein roter Balken sagt, dass etwas nicht stimmt. Eine Störungsmeldung sagt *was* —
und sagt es weiter, während sich das Bild ändert.

## Eine Störung eröffnen

Eine Störung trägt einen Titel, die Statusseiten, auf denen sie angekündigt wird,
und die betroffenen Monitore — jeder mit einer Auswirkung von `degraded` oder
`down`.

Sie hat immer mindestens einen Verlaufseintrag, die erste Meldung ist also Pflicht.
Sie ist kein Feld, das du später ausfüllst.

```json
{
  "title": "Erhöhte Fehlerraten in der API",
  "message": "Wir untersuchen vermehrte 5xx-Antworten.",
  "statusPageIds": [1],
  "monitors": [{ "monitorId": 3, "impact": "degraded" }]
}
```

![Die Störungsliste: eine offene Störung und eine bereits behobene](/screenshots/de/incidents-list.jpg)

## Sie weiterbewegen

Der Lebenszyklus hat vier Zustände:

::steps{level="3"}

### investigating

Etwas stimmt nicht und ihr schaut es euch an.

### identified

Ihr wisst, was es ist.

### monitoring

Der Fix ist draußen und ihr beobachtet, ob er hält.

### resolved

Erledigt. `resolvedAt` wird gesetzt.

::

::warning
Der Status wird durch **das Posten eines Verlaufseintrags** bewegt, nie durch das
Bearbeiten der Störung. Ein `PATCH` ändert Titel, Statusseiten und betroffene
Monitore — nicht den Zustand.
::

Jedes Update ist eine Meldung plus der Status, auf den es geht, und der Verlauf ist
das, was die öffentliche Seite zeigt. Einen anderen Status als `resolved` nach
einer Auflösung zu posten löscht `resolvedAt` wieder — so wird eine Störung
wiedereröffnet.

![Eine Störung mit ihrem Verlauf — der Status wird durch ein Update bewegt, nie durch Bearbeiten der Störung](/screenshots/de/incident-detail.jpg)

## Wartung planen

Ein Wartungsfenster hat dieselbe Form mit einem anderen Lebenszyklus —
`scheduled`, `in_progress`, `completed` — plus Start- und Endzeit. `endsAt` muss
nach `startsAt` liegen, und eine Änderung, die das Fenster umdrehen würde, wird
abgelehnt.

```json
{
  "title": "Datenbank-Upgrade",
  "message": "Geplantes Upgrade, kurze Unterbrechungen möglich.",
  "startsAt": "2026-09-01 22:00:00",
  "endsAt": "2026-09-02T00:30:00Z",
  "statusPageIds": [1],
  "monitors": [
    { "monitorId": 3, "impact": "degraded" },
    { "monitorId": 4, "impact": "down" }
  ]
}
```

Solange ein Fenster **aktiv** ist — explizit `in_progress`, oder noch `scheduled`
mit bereits vergangener Startzeit — werden seine Monitore auf den angekündigten
Seiten als in Wartung dargestellt, jeweils mit der für sie erklärten Auswirkung.

## Discord mitziehen lassen

Die Discord-Integration bearbeitet ihre Nachricht, während sich die Störung
entwickelt, statt jedes Mal eine neue zu posten. Ein Kanal, der eine zweistündige
Störung verfolgt, endet mit einer Nachricht, die den aktuellen Stand liest — nicht
mit elf, die man der Reihe nach lesen muss.

Siehe [Benachrichtigungen](/de/guide/notifications).

## Aus einem Skript heraus

Alles oben steht über die API mit den Scopes `incidents:write` und
`maintenances:write` zur Verfügung — genau das macht es möglich, eine Störung aus
derselben Pipeline zu eröffnen, die das Problem bemerkt hat. Siehe
[Störungen](/de/api/incidents) und [Wartungen](/de/api/maintenances).
