upcore wird vollständig über die Umgebung konfiguriert. `.env.example` im
Repository dokumentiert jede Variable an Ort und Stelle; diese Seite ist dieselbe
Menge, sortiert danach, was sie entscheidet.

::note
Einstellungen, die zur *Organisation* gehören statt zum Deployment —
Aufbewahrung, Branding der Statusseiten, SSO, Benachrichtigungskanäle — liegen in
der Datenbank und werden im Admin-UI bearbeitet, nicht hier.
::

![Die Einstellungen im Admin-UI: Start-Seite, Sprache der Oberfläche und Datenaufbewahrung](/screenshots/de/settings.jpg)

## Das Pflichtfeld setzen

```ini [.env]
NUXT_SESSION_PASSWORD=
```

Der Schlüssel, mit dem `nuxt-auth-utils` die Session-Cookies verschlüsselt.
Mindestens 32 Zeichen; ihn später zu ändern macht jeden Login ungültig.

```bash [Terminal]
openssl rand -base64 32
```

## Eine Datenbank wählen

| Variable | Standard | |
| --- | --- | --- |
| `DB_DRIVER` | `sqlite` | `sqlite` oder `postgres`. Beides ist vollständig umgesetzt. |
| `DATABASE_URL` | — | Pflicht für `postgres`. Ein Passwort mit Sonderzeichen muss URL-kodiert werden. |
| `UPCORE_DATA_DIR` | `.data` | Wo die SQLite-Datei (`<dir>/upcore.db`) und hochgeladene Icons (`<dir>/icons`) liegen. Im Container `/data`, aus einem Volume. |
| `DB_FILE` | — | Überschreibt den SQLite-Pfad, wenn die Datei nicht unter `UPCORE_DATA_DIR` liegen soll. |

Im Docker-Stack mit dem Postgres-Override wird `DATABASE_URL` aus
`POSTGRES_USER`, `POSTGRES_PASSWORD` und `POSTGRES_DB` gebaut und muss hier nicht
gesetzt werden.

::warning
Ein Wechsel von `DB_DRIVER` verschiebt **keine** Daten — die andere Datenbank
startet leer.
::

Siehe [Datenbanken](/de/operations/databases), was die Zwei-Treiber-Regel in der
Praxis bedeutet.

## Die App veröffentlichen

| Variable | Standard | |
| --- | --- | --- |
| `APP_BIND` | `127.0.0.1` | Adresse, auf der der Container veröffentlicht. |
| `APP_PORT` | `3000` | Port. |
| `NUXT_PUBLIC_APP_URL` | — | Absolute Basis-URL dieser Instanz. Wird für die Links in Discord-Nachrichten genutzt; ohne sie tragen diese Nachrichten keinen Link. |
| `UPCORE_IMAGE` / `UPCORE_TAG` | GHCR / `latest` | Welches Image der Stack fährt. |

`127.0.0.1` ist Absicht: TLS gehört in einen Reverse-Proxy vor upcore. Auf
`0.0.0.0` läge dasselbe Klartext-HTTP — und jeder Login darüber — im Netz.

## Festlegen, wer sich registrieren darf

```ini [.env]
NUXT_REGISTRATION_ENABLED=false
```

Standardmäßig aus. `/register` existiert nicht und `/api/auth/register` antwortet
mit `403`: eine Instanz, die nie öffentlich sein sollte, darf nicht durch ein
Update öffentlich werden.

Registrieren heißt, der einen Organisation beizutreten, die diese Instanz ist.
Das neue Mitglied ist `editor`; unter `/admin/users` kannst du es befördern.
Admin an jeden zu geben, der die URL findet, ist kein Standard.

Registrierung läuft nie vor dem Setup: solange kein Konto existiert, zeigt
`/login` das Formular für den ersten Admin, und das legt ihn an.

## Mail versenden

Ein leeres `NUXT_SMTP_HOST` — der Standard — heißt, dass upcore **gar keine Mail**
verschickt: keine Adressbestätigung, kein Passwort-Reset, keine Willkommensmail,
und `/api/auth/password-reset` antwortet mit `404`.

| Variable | Standard | |
| --- | --- | --- |
| `NUXT_SMTP_HOST` | — | Das Relay. Leer = keine Mail. |
| `NUXT_SMTP_PORT` | `587` | `587` spricht STARTTLS, `465` ist implizites TLS und wird allein am Port erkannt. |
| `NUXT_SMTP_SECURE` | `false` | Erzwingt implizites TLS auf einem anderen Port. Fast nie nötig. |
| `NUXT_SMTP_REQUIRE_TLS` | `true` | Verweigert den Versand über eine Verbindung, die nicht verschlüsselt werden konnte. |
| `NUXT_SMTP_USER` / `NUXT_SMTP_PASSWORD` | — | Leer für ein lokales MTA ohne Authentifizierung. |
| `NUXT_SMTP_FROM` | `NUXT_SMTP_USER` | Die Absenderadresse, wenn der Benutzer eine ist. |
| `NUXT_SMTP_FROM_NAME` | `upcore` | Der Name davor. |
| `NUXT_SMTP_REPLY_TO` | — | Nur sinnvoll, wenn jemand die Antworten liest. |
| `NUXT_SMTP_REJECT_UNAUTHORIZED` | `true` | Zertifikat des Relays prüfen. |
| `NUXT_EMAIL_VERIFICATION` | `true` | Ob ein selbst registriertes Konto seine Adresse bestätigen muss, bevor es sich anmelden kann. |

::note
`NUXT_EMAIL_VERIFICATION` entscheidet nur dort etwas, wo ein Relay existiert.
Genau das macht die Bestätigungspflicht sicher: eine Instanz, die die
Bestätigungsmail nicht senden kann, legt nie ein Konto an, das auf eine wartet.
::

Siehe [Mail](/de/operations/mail) für den vollständigen Ablauf.

## Hinter einem Proxy laufen

```ini [.env]
NUXT_TRUST_PROXY=false
```

Liest die Client-IP aus `x-forwarded-for`. Nur hinter einem Proxy aktivieren,
**den du kontrollierst**: die CIDR-Bindung von API-Keys hängt daran, und ein
nicht vertrauenswürdiger Proxy lässt Aufrufer ihre Quelladresse selbst wählen —
womit die Bindung wertlos ist.

## Mehr als einen Container betreiben

```ini [.env]
NUXT_SCHEDULER=auto
```

Wer die Hintergrund-Schedules ausführt: die Monitor-Checks, die
Outpost-Verifizierungs-Retries, den Aufbewahrungslauf, den Discord-Abgleich.

| Wert | |
| --- | --- |
| `auto` | Der Standard, und für jedes Deployment richtig. Die Schedules werden in der Datenbank geleast, also führt genau ein Prozess sie aus — egal wie viele es gibt. |
| `off` | Dieser Prozess bedient HTTP und sonst nichts. |
| `on` | Dieser Prozess führt sie immer aus, ohne zu fragen. |

`off`/`on` sind dafür da, die Rollen aufzuteilen statt eine zu wählen: `off` auf
den Web-Replicas, `on` auf einem dedizierten Runner-Service. `on` prüft nichts,
also verdoppeln zwei Prozesse mit `on` jeden Check.

Siehe [Mehr als ein Container](/de/operations/scaling).

## Zeitzone setzen

```ini [.env]
TZ=Europe/Berlin
```

Gespeichert wird immer in UTC; das hier betrifft nur Log-Zeitstempel und was der
Runner meldet.
