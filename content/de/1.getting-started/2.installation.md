## Voraussetzungen prüfen

- **Docker** mit Compose-Plugin. Das ist die gesamte Laufzeitanforderung — kein
  Datenbankserver, kein Node auf dem Host, kein Build-Tooling.
- **Ein Reverse-Proxy** davor für TLS. upcore bindet bewusst auf
  `127.0.0.1:3000`; dasselbe Klartext-HTTP auf `0.0.0.0` hätte jeden Login im
  Netz.
- **`openssl`**, oder irgendeine andere Quelle für 32 zufällige Zeichen.

## Mit Docker starten

::steps{level="3"}

### Repository klonen

```bash [Terminal]
git clone https://github.com/upcore-app/upcore.git
cd upcore
```

### Umgebungsdatei anlegen

```bash [Terminal]
cp .env.example .env
```

Jede Variable in dieser Datei ist an Ort und Stelle dokumentiert. Genau eine muss
gesetzt sein, bevor der Stack startet.

### Session-Schlüssel setzen

`NUXT_SESSION_PASSWORD` verschlüsselt die Session-Cookies und muss mindestens 32
Zeichen lang sein. Ihn später zu ändern macht jeden Login ungültig.

```bash [Terminal]
openssl rand -base64 32
```

Das Ergebnis in `.env` eintragen:

```ini [.env]
NUXT_SESSION_PASSWORD=xJ4k…
```

### Stack starten

```bash [Terminal]
docker compose up -d
```

Das ist das ganze Deployment: SQLite in einem Volume, kein Datenbankserver.

::

Ruf `http://127.0.0.1:3000` auf — über deinen Proxy unter der Adresse, die du ihm
gegeben hast — und beim ersten Start wirst du nach dem Admin-Konto gefragt. Es
gibt kein Standardpasswort und keinen vorangelegten Benutzer: solange kein Konto
existiert, zeigt `/login` das Formular für den ersten Admin, und dieses Formular
legt ihn an.

::tip
`GET /api/health` meldet, ob die Datenbank antwortet **und** ob die Migrationen
gelaufen sind. Das ist, was der Container-Healthcheck aufruft, und es ist
öffentlich — richte dein eigenes Monitoring darauf.
::

## Stattdessen PostgreSQL nutzen

Override-Datei ergänzen und ein Passwort in `.env` setzen:

```ini [.env]
POSTGRES_PASSWORD=…
```

```bash [Terminal]
openssl rand -hex 24
```

```bash [Terminal]
docker compose -f docker-compose.yml -f docker-compose.postgres.yml up -d
```

::warning
Ein Wechsel von `DB_DRIVER` verschiebt keine Daten. Die andere Datenbank startet
leer. Entscheide dich, bevor du Zeilen hast, die dir etwas wert sind — oder
migriere sie selbst.
::

Ein alphanumerisches Passwort spart einen Schritt: der Wert landet in einer
Verbindungs-URL, in der Sonderzeichen prozentkodiert werden müssen.

## Ein Image festnageln

`.github/workflows/docker.yml` pusht zwei Images nach GHCR, **wenn ein Release
veröffentlicht wird**:

| Image | Was es ist |
| --- | --- |
| `ghcr.io/upcore-app/upcore:<tag>` | die App — das Nitro-Bundle auf Node, kein Quellcode, kein Build-Tooling |
| `ghcr.io/upcore-app/upcore:<tag>-migrate` | der Migrations-Runner — die zwei Datenbanktreiber und die SQL-Dateien |

Sie werden immer zusammen gepusht: ein `migrate`-Image, das älter ist als die App,
würde ein Schema anlegen, das die App nicht erwartet.

Ein Release `v1.2.3` veröffentlicht `1.2.3`, `1.2` und `1` — ein Deployment kann
also festlegen, wie weit es mitgeht. `latest` bewegt sich nur bei einem
vollständigen Release, nie bei einem Pre-Release und nie, weil etwas gemerged
wurde.

```ini [.env]
UPCORE_TAG=1.2
```

`docker compose build` baut stattdessen beide Images aus deinem Checkout.

## Aus dem Quellcode betreiben

Für die Entwicklung, oder um gegen einen Checkout statt gegen ein Image zu laufen.

::steps{level="3"}

### Abhängigkeiten installieren

`bun.lock` ist die Lockdatei — es gibt keine `package-lock.json`, und eine wieder
hinzuzufügen gäbe Image und Entwicklermaschine zwei verschiedene
Abhängigkeitsbäume.

```bash [Terminal]
bun install
```

### Konfigurieren

```bash [Terminal]
cp .env.example .env   # dann NUXT_SESSION_PASSWORD setzen
```

### Dev-Server starten

```bash [Terminal]
bun run dev
```

Das wendet zuerst die Migrationen an und startet dann Nuxt auf
`http://localhost:3000`.

::

::note{title="bun installiert, node führt aus"}
bun ist nur der Paketmanager. Der Nuxt-Build, der Migrations-Runner und der
ausgelieferte Server laufen alle unter node — deshalb löst `better-sqlite3` das
vorgebaute Binary für Nodes ABI auf, und deshalb basiert das Dockerfile auf
`node:22-slim` mit hineinkopiertem bun-Binary.
::

### Lokal gegen PostgreSQL arbeiten

```bash [Terminal]
docker run -d --name upcore-pg -p 5432:5432 \
  -e POSTGRES_USER=upcore -e POSTGRES_PASSWORD=upcore -e POSTGRES_DB=upcore \
  postgres:17-alpine

DB_DRIVER=postgres DATABASE_URL=postgres://upcore:upcore@localhost:5432/upcore bun run dev
```

## Eine Instanz aktualisieren

```bash [Terminal]
docker compose pull && docker compose up -d
```

Der `migrate`-Service läuft zuerst, bringt das Schema auf Stand und beendet sich;
der App-Container startet erst, wenn er mit Exit-Code 0 fertig ist. Schlägt das
fehl, ist das ein echter Fehler — eine kaputte Migration oder eine nicht
erreichbare Datenbank — und die App startet bewusst **gar nicht**, statt gegen ein
Schema zu laufen, das nicht zum Code passt:

```bash [Terminal]
docker compose logs migrate
```

::note
Eine bestehende SQLite-Datenbank aus der Zeit vor den Migrationen wird beim ersten
Lauf übernommen: fehlende Spalten werden ergänzt, dann wird sie als migriert
vermerkt.
::
