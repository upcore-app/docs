| Methode | Pfad | Scope |
| --- | --- | --- |
| `GET` | `/api/v1/maintenances` | `maintenances:read` |
| `POST` | `/api/v1/maintenances` | `maintenances:write` |
| `GET` | `/api/v1/maintenances/{id}` | `maintenances:read` |
| `PATCH` | `/api/v1/maintenances/{id}` | `maintenances:write` |
| `DELETE` | `/api/v1/maintenances/{id}` | `maintenances:write` |
| `POST` | `/api/v1/maintenances/{id}/updates` | `maintenances:write` |

Filter auf der Listenroute: `status`, `statusPageId`.

Die Status sind `scheduled`, `in_progress` und `completed` und werden — wie bei
Störungen — durch das Posten eines Verlaufseintrags bewegt.

## Ein Fenster planen

```bash [Terminal]
curl -X POST https://status.example.com/api/v1/maintenances \
  -H "Authorization: Bearer $UPCORE_KEY" -H 'Content-Type: application/json' \
  -d '{
        "title": "Datenbank-Upgrade",
        "message": "Geplantes Upgrade, kurze Unterbrechungen möglich.",
        "startsAt": "2026-09-01 22:00:00",
        "endsAt": "2026-09-02T00:30:00Z",
        "statusPageIds": [1],
        "monitors": [
          { "monitorId": 3, "impact": "degraded" },
          { "monitorId": 4, "impact": "down" }
        ]
      }'
```

`endsAt` muss nach `startsAt` liegen. Ein `PATCH`, der das Fenster umdrehen würde,
wird abgelehnt.

## `active` lesen

Die Antwort trägt `active`: ob das Fenster **gerade jetzt** läuft — entweder
explizit `in_progress`, oder noch `scheduled` mit bereits vergangener Startzeit.

Solange ein Fenster aktiv ist, werden seine Monitore auf den angekündigten
Statusseiten als in Wartung dargestellt, jeweils mit der für sie erklärten
`impact` — `degraded` oder `down`, standardmäßig `degraded`.
