- **Basispfad:** `/api/v1`
- **Spezifikation:** `GET /api/v1/openapi.json`, erzeugt aus denselben
  zod-Schemas, gegen die die Endpunkte validieren
- **Interaktive Doku:** `/api-docs` auf deiner Instanz

Weil die Spezifikation aus der Validierung erzeugt wird, kann sie keinen Endpunkt
beschreiben, den es nicht gibt.

## Einen Key mitschicken

Jeder Request braucht einen API-Key, auf einem von zwei Wegen:

::code-group
```bash [Authorization]
curl -H "Authorization: Bearer upc_ac262397_3307862…" \
     https://status.example.com/api/v1/monitors
```

```bash [X-API-Key]
curl -H "X-API-Key: upc_ac262397_3307862…" \
     https://status.example.com/api/v1/monitors
```
::

Keys werden im Admin-UI unter **API-Keys** angelegt, Admin-Rolle vorausgesetzt.
Das Token hat die Form `upc_<prefix>_<secret>` und wird **genau einmal** angezeigt
— gespeichert wird nur `sha256(secret)`, ein verlorener Key wird also ersetzt,
nicht wiederhergestellt.

::note
Das Session-Cookie eines angemeldeten Admins wird als Fallback akzeptiert. Genau
das lässt den „Test-Request“-Knopf auf `/api-docs` funktionieren; Skripte sollten
immer einen Key benutzen.
::

Die Key-Verwaltung ist nicht über `/api/v1` erreichbar. Ein Key kann nie einen
anderen anlegen, ändern oder lesen.

## Scopes vergeben

| Scope | Erlaubt |
| --- | --- |
| `monitors:read` | Monitore auflisten und lesen |
| `monitors:write` | Monitore anlegen, ändern, löschen |
| `incidents:read` | Störungen auflisten und lesen |
| `incidents:write` | Störungen anlegen, ändern, löschen und Verlaufseinträge posten |
| `maintenances:read` | Wartungsfenster auflisten und lesen |
| `maintenances:write` | Fenster anlegen, ändern, löschen und Verlaufseinträge posten |

`<resource>:write` schließt `<resource>:read` ein. Ein Request ohne den nötigen
Scope liefert `403`.

## Einen Key an ein Netz binden

Ein Key kann auf eine Liste von Netzen beschränkt werden. Ein Request von einer
anderen Adresse wird mit `403` abgelehnt, auch wenn der Key selbst gültig ist.

```
203.0.113.0/24
2001:db8::/32
198.51.100.7
```

IPv4 und IPv6 werden unterstützt; eine nackte Adresse bindet den Key an genau
diesen Host. Eine leere Liste erlaubt jede Quelladresse.

Host-Bits werden beim Speichern normalisiert, `10.1.2.3/8` wird also als
`10.0.0.0/8` gespeichert — und so verglichen. Eine IPv4-Adresse, die über einen
Dual-Stack-Listener als `::ffff:203.0.113.7` ankommt, passt weiterhin auf ein
IPv4-Netz. Ein Netz der einen Familie passt nie auf eine Adresse der anderen:
`0.0.0.0/0` öffnet die Tür nicht für IPv6.

::warning{title="Hinter einem Reverse-Proxy"}
Setz `NUXT_TRUST_PROXY=true`, damit die Quelladresse aus `x-forwarded-for`
gelesen wird. Ohne das nutzt die Prüfung die TCP-Peer-Adresse, hinter einem Proxy
also den Proxy selbst — jeder gebundene Key würde abgelehnt.

Aktiviere es nur, wenn der Proxy einer ist, den du kontrollierst. Sonst setzt der
Aufrufer den Header selbst und die Bindung ist wertlos.
::

In der Entwicklung wird der Header immer vertraut, weil Requests über den
Dev-Proxy von Vite ankommen und die Socket-Adresse dort nicht sichtbar ist. In
einem Produktions-Build entscheidet allein `NUXT_TRUST_PROXY`.

## Ablauf und Widerruf

Ein Key kann ein `expiresAt` tragen. Abgelaufene und deaktivierte Keys liefern
`401`. Einen Key zu löschen wirkt sofort.

## Einen Fehler lesen

Jede Antwort außerhalb von 2xx nutzt einen Umschlag:

```json
{
  "statusCode": 400,
  "statusMessage": "Invalid request body: target — HTTP target must start with http:// or https://",
  "data": {
    "issues": [
      {
        "path": "target",
        "message": "HTTP target must start with http:// or https://",
        "code": "custom"
      }
    ]
  }
}
```

`data.issues` steht bei Validierungsfehlern und benennt jedes beanstandete Feld.

| Status | Bedeutung |
| --- | --- |
| `400` | ungültiger Body, Query- oder Pfadparameter; oder eine referenzierte ID existiert nicht |
| `401` | kein Key, unbekannter Key, deaktivierter Key, abgelaufener Key |
| `403` | Key hat den Scope nicht, oder der Request kam von außerhalb seiner CIDR-Bindung |
| `404` | die angesprochene Ressource existiert nicht |

## Den Konventionen folgen

- Alle Bodys sind JSON.
- `PATCH` ist eine Teiländerung: nur die gesendeten Felder ändern sich. Ein
  explizites `null` leert ein nullbares Feld.
- Zeitstempel sind UTC. Datumszeiten werden als `YYYY-MM-DD HH:MM:SS` oder ISO 8601
  angenommen und immer als `YYYY-MM-DD HH:MM:SS` zurückgegeben.
- Listen-Endpunkte nehmen `limit` (1–200, Standard 50) und `offset`.
- IDs, die in einem Body referenziert werden — Monitore, Statusseiten,
  Benachrichtigungen — werden geprüft, bevor irgendetwas geschrieben wird. Eine
  falsche Referenz hinterlässt also nie eine halbe Ressource.

## Die Organisation benennen

Auf der eigenen Subdomain einer Organisation müssen Key und Host übereinstimmen.
Auf einem Host, unter dem keine Organisation aufgelöst wird, liefert der Key sie — ein Client muss
also das Hostnamen-Layout nicht kennen.
